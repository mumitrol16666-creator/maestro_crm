# Полный аудит Maestro CRM

> Исторический снимок на 30 августа. Текущий статус и закрытие блокеров зафиксированы в
> [MAESTRO_FINAL_DEPLOYMENT_2026-08-31.md](./MAESTRO_FINAL_DEPLOYMENT_2026-08-31.md).
> Решение `NO-GO` ниже нельзя использовать как актуальный статус релиза без нового отчёта.

**Дата:** 30 августа 2026 г.
**Контур:** изолированный локальный QA-стенд
**Решение о выпуске:** **NO-GO**

## Обновление после аудита

После фиксации отчета локально выполнен первый пакет hardening:

- неактивный аккаунт теперь отклоняется при login и на каждом запросе; старый JWT перестает работать сразу после деактивации;
- пароль нужен маршруту только для проверки и хеширования, но `currentPassword`, `newPassword`, токены и секреты рекурсивно маскируются в `ActivityLog`;
- публичная заявка ограничивает длины и формат телефона, отвергает HTML-разметку, а найденные frontend-выводы экранируются;
- Telegram credentials удалены из frontend и локальных config-файлов; backend принимает их только из environment;
- production compose больше не публикует PostgreSQL, требует явные DB credentials и привязывает backend к loopback;
- локальные PostgreSQL, Redis, backend и frontend также привязаны к loopback; контейнеры пересозданы без потери volume;
- добавлены 3 security regression tests; QA API подтвердил отзыв inactive-сессии, маскировку двух реальных смен пароля и отклонение вредоносной заявки без записи в БД.

Владелец продукта подтвердил перевыпуск Telegram bot token 30 августа 2026 года. Новый токен должен оставаться только в server environment. Перед production-релизом еще требуется убедиться, что старое значение отсутствует в image layers, backup, логах и deploy-артефактах.

SEC-01 по решению владельца продукта пока не изменен. С точки зрения аудита возможность обычного `admin` управлять `super_admin` остается критическим риском и одной из причин статуса NO-GO.

## 1. Краткий итог

CRM функционально развита: основные разделы работают, критические финансовые операции защищены от повторного выполнения, тесты проходят, схема тестовой базы целостна, а резервная копия успешно восстанавливается. Однако выпускать текущую версию в production нельзя.

Причины NO-GO:

1. Администратор может повысить себя или другого пользователя до `super_admin`.
2. В админском интерфейсе есть доказанный путь сохраненного XSS через данные заявки.
3. Смена пароля может записать старый и новый пароль в `ActivityLog` открытым текстом.
4. Деактивированный пользователь сохраняет доступ по существующему JWT и может снова войти.
5. В локально доступных frontend-файлах был обнаружен Telegram credential; владелец подтвердил его перевыпуск, но старое значение еще нужно исключить из image layers, backup, логов и deploy-артефактов.
6. Параллельное создание одинакового занятия разными запросами создает дубль.
7. Схема production обновляется через `prisma db push`, без версионированных миграций и безопасного отката.
8. Ключевые CRM-экраны на телефоне обрезаются и местами недоступны для управления.

До закрытия этих пунктов готовность к production не подтверждена.

## 4. Критические блокеры

### SEC-01. Повышение роли до super_admin

**Серьезность:** Critical
**Статус:** подтверждено по маршрутам и проверкам ролей

Обычный пользователь с ролью `admin` может создать пользователя с ролью `super_admin`. Тот же общий маршрут редактирования позволяет сбросить пароль существующему `super_admin`, не проверяя уровень целевого пользователя.

Код:

- `backend/src/routes/users.js:632-687`
- `backend/src/routes/users.js:694-784`

Что исправить:

- разрешить создание и изменение `super_admin` только действующему `super_admin`;
- запретить `admin` менять роль, пароль и статус учетной записи выше своей роли;
- добавить отдельные backend-тесты на вертикальную эскалацию;
- записывать такие действия в защищенный аудит без чувствительных данных.

### SEC-02. Сохраненный XSS в заявках

**Серьезность:** High
**Статус:** подтвержден сквозной поток данных; тестовая запись после проверки удалена

Публичная заявка принимает произвольную строку в поле телефона. Затем значение попадает в HTML таблицы и WhatsApp-ссылки без безопасного экранирования. Это позволяет выполнить JavaScript в браузере администратора. Поскольку JWT хранится в `localStorage`, последствия включают захват административной сессии.

Код:

- `frontend/js/modules/bookings/bookings.js:351-368`
- `frontend/js/modules/bookings/bookings.js:978-1001`

Что исправить:

- валидировать и нормализовать телефон на backend;
- использовать `textContent`, DOM API и безопасные атрибуты вместо HTML-конкатенации;
- экранировать все серверные строки перед вставкой в HTML;
- добавить CSP и отказаться от хранения административного токена в доступном JavaScript хранилище;
- добавить E2E-тесты с вредоносными значениями для каждого публичного поля.

### SEC-03. Пароли могут попадать в ActivityLog

**Серьезность:** High
**Статус:** подтверждено по коду

При смене пароля поля `currentPassword` и `newPassword` могут сохраняться в metadata/details журнала. Текущая маскировка скрывает только поле с точным именем `password`.

Код:

- `backend/src/routes/auth.js:134-177`
- `backend/src/middleware/activityLogger.js:200-208`
- `backend/src/middleware/activityLogger.js:251-281`
- `backend/src/middleware/activityLogger.js:313-349`

Что исправить:

- перейти от черного списка полей к белому списку разрешенных данных аудита;
- рекурсивно скрывать `password`, `currentPassword`, `newPassword`, `token`, `secret`, `authorization`, cookie и похожие поля;
- проверить и очистить production-журнал отдельным безопасным скриптом;
- принудительно сменить затронутые пароли, если такие записи найдутся.

### SEC-04. Деактивированная учетная запись сохраняет доступ

**Серьезность:** High
**Статус:** подтверждено по логике авторизации

Login и middleware проверяют подпись JWT и пользователя, но не блокируют неактивный статус. Ранее выданный токен действует до 7 дней; механизма отзыва нет.

Код:

- `backend/src/routes/auth.js:12-50`
- `backend/src/middleware/auth.js:39-81`

Что исправить:

- проверять активный статус при login и на каждом защищенном запросе;
- внедрить `tokenVersion` или серверный реестр сессий;
- отзывать все сессии при деактивации, смене роли и пароля;
- сократить срок access token и добавить безопасный refresh flow.

### SEC-05. Telegram credential доступен из frontend

**Серьезность:** High
**Статус:** локальная экспозиция устранена, перевыпуск подтвержден владельцем; наличие старого значения в серверных артефактах не проверялось

Credential обнаружен в `frontend/js/telegram-config.js` и соответствующем min-файле. На QA эти файлы отдавались HTTP-сервером. Секрет нельзя считать безопасным, даже если файл исключен из Git.

Что выполнено и что осталось:

- credential перевыпущен по подтверждению владельца продукта;
- credential удален из frontend и локальных config-файлов;
- проверить и удалить старое значение из image layers, backup, логов и deploy-артефактов;
- все вызовы Telegram выполнять только на backend;
- добавить secret scanning в CI и pre-commit;
- проверить локальные deploy-логи на случайно сохраненные credentials.

### DATA-01. Дубли одинакового занятия

**Серьезность:** High
**Статус:** исправлено локально и проверено на отдельной PostgreSQL-базе; в production не развернуто

Первичный конкурентный тест воспроизводил дефект: два параллельных запроса с разными idempotency key, но одинаковыми группой, кабинетом, преподавателем и временем, оба возвращали 201 и создавали две записи.

Локальное исправление:

- все мутации расписания используют PostgreSQL transaction advisory locks по учебной дате и ресурсам занятия: кабинет, преподаватель, группа и ученик;
- после получения блокировок пересечение повторно проверяется внутри той же транзакции перед записью;
- создание, перенос, восстановление отмененного занятия, пробные занятия, замена назначенного преподавателя и автоматическая генерация используют общий guard;
- соседние полуинтервалы разрешены, отмененные занятия освобождают слот;
- явный административный режим `ignoreConflicts` сохранен;
- дата нормализуется относительно учебного часового пояса, чтобы локальная полночь и UTC не создавали разные ключи блокировки.

Проверка исправления:

- 6/6 unit-тестов общего guard;
- 6/6 API-сценариев конкуренции и отката на отдельной PostgreSQL-базе;
- 1/1 прямой DB concurrency-тест;
- 2/2 теста автоматической генерации регулярного расписания.

Ожидаемое поведение подтверждено: из двух параллельных конфликтующих запросов один получает 201, второй 409, в БД остается одно занятие.

Ограничения перед production-релизом:

- исправление еще не развернуто и должно пройти staging smoke test;
- занятия без преподавателя, кабинета, группы и ученика не имеют ресурса для определения бизнес-конфликта; для них требуется отдельное продуктовое правило;
- состояние фоновой генерации по-прежнему хранится в памяти процесса и должно быть перенесено в надежную очередь или БД.

### DEPLOY-01. Небезопасное изменение схемы и данных при деплое

**Серьезность:** High
**Статус:** подтверждено по deploy-скрипту

В `backend/prisma/migrations` нет истории миграций. Деплой выполняет `prisma db push`, затем reconciliation-скрипты, пока старый процесс еще может записывать данные. Без миграционного журнала, preflight и rollback это создает риск потери или повторного пересчета данных.

Код:

- `deploy/deploy.sh:48-69`

Что исправить:

- создать базовую Prisma migration и перейти на `prisma migrate deploy`;
- репетировать миграцию на копии production backup;
- разделить backward-compatible schema deploy и переключение приложения;
- выполнять reconciliation один раз под блокировкой и после остановки конфликтующих записей;
- добавить автоматический rollback приложения и документированный rollback данных.

## 5. Высокие и средние риски

### Разрешения и данные

- `RolePermissions` в основном управляет видимостью интерфейса, но не является полной backend-границей. Сотрудник с пустыми разрешениями может обращаться к части маршрутов групп, учеников, занятий и статистики.
- Скрытие раздела в меню не считается защитой: API должен проверять permission на каждом чувствительном маршруте.
- SSO-токен передается в query string и может попасть в историю браузера и промежуточные журналы.

### Публичные маршруты и интеграции

- На login, публичных заявках и marketing endpoints нет подтвержденного rate limit. Серия неверных логинов не вернула 429.
- Meta webhook работает fail-open, если app secret не задан. В production он должен отказываться запускаться без секрета.
- Socket.IO handshake доступен без JWT. Чужой browser Origin отклоняется, но клиент без Origin подключается и может получать служебные идентификаторы событий.
- Публичная заявка должна требовать или генерировать server-side idempotency key, а не полагаться только на текущий frontend.

### Idempotency и журналы

- Глобальный idempotency middleware создает записи до авторизации: анонимный клиент может раздувать таблицу уникальными ключами.
- В кеше idempotency может храниться полный response body, включая чувствительные одноразовые значения.
- На QA все 34 записи `IdempotencyKey` уже были просрочены; общего cleanup job нет.
- `IntegrationLog` вырос до 12 598 строк примерно за 26 часов, около 8 MB. Каждое интеграционное чтение журналируется, retention отсутствует.
- Нужны TTL, пакетная очистка, метрики роста и запрет сохранения секретов/паролей в ответах.

### Зависимости и browser security

- `npm audit --omit=dev` нашел 5 high и 1 moderate уязвимость в production-зависимостях.
- FullCalendar, Socket.IO и XLSX загружаются с CDN без SRI.
- CSP отключена.
- JWT хранится в `localStorage`, что усиливает последствия XSS.

### Health check и наблюдаемость

- `/health` подтверждает только работу процесса и не проверяет БД и Redis (`backend/src/server.js:175-181`).
- При ошибке подключения к БД приложение может продолжить отвечать поверхностным health check.
- Frontend отправляет performance/error данные на `/api/performance/metrics` и `/errors`, но backend-маршрутов нет.
- `performance.html` обращается к отсутствующему `/api/performance/stats`.
- Эти мертвые запросы создают 404, шум и лишние idempotency-записи.

### Контейнеры и deploy

- Основной `docker-compose.yml` публикует БД и backend на все интерфейсы и содержит небезопасные placeholder-пароли.
- `docker-compose.local.yml` публикует Postgres, Redis и backend в локальную сеть и использует известные development credentials. На общем Wi-Fi это опасно.
- Backend image собирается через `COPY . .`, а `.dockerignore` не гарантирует исключение `.env` из слоев и cache.
- Deploy workflow работает по SSH от root, использует mutable action tags и обновляет `main`, а не проверенный commit SHA.
- Nginx-шаблон не дает доказанной гарантии HTTP -> HTTPS redirect; реальный production-конфиг не проверялся.

## 6. Дубли и конкурентные операции

### Что работает хорошо

Frontend API-слой:

- блокирует повторную отправку формы;
- объединяет одинаковые mutation-запросы в полете;
- добавляет `X-Idempotency-Key`.

Backend middleware поддерживает idempotency глобально (`backend/src/server.js:163-169`).

Все 18 тестов конкуренции прошли для:

- платежа и возврата;
- перевода и финансовой корректировки;
- подтверждения занятия и посещаемости;
- создания и выплаты зарплатной ведомости;
- подтверждения заморозки;
- пробной записи;
- ключевых integration contracts.

### Что осталось уязвимым

- локальная защита бизнес-уникальности занятия еще не выпущена в production;
- для занятий без преподавателя, кабинета, группы и ученика не определено правило бизнес-уникальности;
- генерация расписания хранит состояние job только в памяти процесса;
- публичный backend не должен доверять наличию защиты только в текущем frontend;
- idempotency key не заменяет бизнес-ограничения уникальности; локальное исправление использует отдельные DB-блокировки и повторную проверку.

### Риски производительности

1. снять `EXPLAIN (ANALYZE, BUFFERS)` на реальной копии данных;
2. добавить индексы отдельной migration;
3. проверить write overhead и размер индексов;

| Напоминания | область до ~960 px |
| Абонементы | Kanban до ~784 px |
| Зарплата | таблица до ~1041 px |
| Пользователи | таблица до ~1371 px |
| Аналитика | часть данных обрезана |

`body` при этом остается шириной viewport, поэтому часть контента не превращается в понятный горизонтальный скролл, а становится недоступной.

Дополнительно:

- после изменения размера mobile -> desktop sidebar оставался за пределами экрана до перезагрузки;
- часть touch targets имеет размер 18-31 px вместо рекомендуемых минимум 44 px;
- у большинства modal нет `role="dialog"`, `aria-modal`, переноса focus и надежного закрытия по Escape;
- кнопки закрытия часто 28x28 и без `aria-label`;
- из 275 проверенных controls как минимум 80 не имеют надежного программного label;
- один icon-only button не имеет доступного имени.

Рекомендация: не уменьшать desktop-таблицы до нечитаемого состояния. Для mobile нужны отдельные компактные карточки, drawer для фильтров, sticky primary action и контролируемый scroll внутри таблиц.

## 9. Лишнее и технический долг

- 12 старых локальных `.min.js` файлов синтаксически повреждены, хотя текущие страницы их не загружают. Их нужно удалить или пересобирать автоматически, чтобы случайно не вернуть в production.
- Локальная Nginx-конфигурация не проксирует `/socket.io/`, production-конфигурация проксирует. QA и production должны использовать одну проверяемую схему.
- QA backend image не включает директорию тестов, поэтому команда syntax/test внутри контейнера не соответствует production build.
- Мертвые performance endpoints и orphan-страница должны быть либо завершены, либо удалены.
- Локальные deploy output logs могут содержать credential material. Их нельзя хранить рядом с проектом; найденные значения нужно считать скомпрометированными и заменить.

## 10. Что уже сделано правильно

- CRM остается источником истины для учеников, групп, формата занятий, расписания и финансовых операций.
- Учительские и ученические роли не получают прямой вход в CRM.
- Роль пользователя перечитывается из БД на запросах, поэтому смена роли применяется без ожидания окончания JWT.
- Основные финансовые и зарплатные операции выдержали конкурентные тесты.
- QA-конфигурация изолирует БД и backend на loopback и требует явного dump для загрузки данных.
- Integration API использует service secret и маскирует значимую часть чувствительных данных.
- WhatsApp worker имеет отдельную авторизацию и контролируемое QR-хранилище.
- Backup QA-базы действительно восстанавливается.

## 12. Критерии GO

Решение можно изменить с NO-GO на GO только после того, как:

- закрыты SEC-01..SEC-05, DATA-01 и DEPLOY-01;
- security regression и 18 concurrency tests проходят;
- migration успешно применена к свежей восстановленной копии production backup;
- backup после миграции также восстанавливается;
- ключевые mobile-разделы доступны на 320/390/430 px без скрытых действий;
- health check падает при недоступной БД и deploy корректно останавливается;
- production secrets перевыпущены и не присутствуют во frontend/image/logs;
- выполнен повторный аудит разрешений для каждой staff-роли;
- выполнен ручной smoke test после staging deploy.

## 13. Финальная оценка

**Функциональность:** высокая.
**Целостность QA-базы:** локальная защита от дубля занятия добавлена и проверена на отдельной БД; production ожидает выпуск.
**Автотесты:** хорошая база, но не хватает browser E2E и миграционного контура.
**Мобильная CRM:** не готова.
**Безопасность:** не готова.
**Процесс deploy/rollback:** не готов к безопасному production-релизу.
**Общий статус:** **NO-GO**.

Первоочередная последовательность: безопасность учетных записей и секретов -> XSS и аудит паролей -> уникальность занятий -> миграции и deploy -> мобильные рабочие экраны -> повторный полный прогон.
