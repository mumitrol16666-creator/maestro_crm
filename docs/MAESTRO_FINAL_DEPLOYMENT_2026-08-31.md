# Финальная подготовка Maestro к деплою

**Дата:** 31 августа 2026 г.
**Контур проверки:** изолированный локальный QA
**Решение:** условный `GO` для кода. Production не изменялся.

## 1. Что подтверждено

- CRM: 194 обычных теста и 24 DB-теста прошли.
- Learning Platform: 150 backend-тестов прошли; frontend собрал 45 маршрутов.
- Playwright: 116 из 116 сценариев прошли на desktop и mobile.
- Полный цикл CRM -> приложение -> CRM прошел: создание, проведение, подтверждение, закрытие, отмена, перенос, изменение состава и разовая замена преподавателя.
- Миграции развернуты с нуля: CRM 2 из 2, Learning Platform 58 из 58.
- Резервные копии обеих БД восстановлены в чистые базы, число записей совпало.
- Загрузка приватных файлов проверена с S3-совместимым хранилищем и ClamAV, тестовый вредоносный файл блокируется.
- CRM проверена на 16 видимых разделах при 1440x1000 и 390x844: горизонтального переполнения и ошибок страницы нет.
- Runtime dependency audit не нашел известных уязвимостей. Оставшиеся предупреждения относятся к build-time Prisma CLI и не входят в runtime-контейнер.

## 2. Что нужно до первого production-запуска

1. Зафиксировать точные Git SHA обоих репозиториев. Деплой только по SHA, не по плавающей ветке.
2. Проверить реальные production `.env` без вывода секретов в терминал или логи.
3. Подготовить приватное S3-совместимое хранилище и ClamAV для файлов сообщений и домашних заданий.
4. Проверить свободное место, RAM, TLS, DNS и firewall VPS. PostgreSQL, Redis, MinIO и ClamAV не должны быть доступны извне.
5. Убедиться, что старый Telegram bot token отсутствует в Git, образах, логах и резервных копиях. Новый токен хранить только в server environment.
6. Настроить и вручную проверить зашифрованную резервную копию до выкладки.
7. Снять отдельные pre-deploy backup обеих production-БД и сохранить пути к ним.

Push в `main` выполняет только CI-проверки. Production-деплой запускается вручную
после успешного CI в обоих репозиториях через workflow CRM с целью `all`.

Принятый владельцем риск: обычный `admin` пока может управлять `super_admin`. Это сознательное продуктовое решение, а не пропущенный дефект.

## 3. Обязательные переменные Learning Platform

- `DATABASE_URL`
- `JWT_SECRET` длиной не менее 32 случайных символов
- `CORS_ORIGIN` с production-доменом
- CRM integration URL и секреты только из production environment
- `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`
- `S3_FORCE_PATH_STYLE` в соответствии с провайдером
- `S3_SERVER_SIDE_ENCRYPTION`, если поддерживается провайдером
- `CLAMAV_HOST`, `CLAMAV_PORT`, `CLAMAV_TIMEOUT_MS`

Перед запуском выполнить release preflight. Он должен завершиться без предупреждений о тестовой БД, слабых секретах, недоступном S3 или ClamAV.

## 4. Ежедневный backup в Telegram

Скрипт: `deploy/backup-maestro-databases.sh`
Systemd: `deploy/systemd/maestro-database-backup.service` и `.timer`

Backup формируется ежедневно около 22:00 по `Asia/Aqtobe`. Обе БД выгружаются через закрепленный `postgres:16-alpine`, проверяются `pg_restore --list`, шифруются `age`, после чего в Telegram отправляются только `.dump.age` и SHA256. Незашифрованный dump удаляется даже при ошибке.

Секреты уведомлений хранить в `/etc/maestro/backup-notify.env`:

```bash
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...
AGE_RECIPIENT=age1...
```

Приватный ключ `age` должен храниться отдельно от VPS. Перед включением таймера обязательно вручную запустить service, скачать оба файла из Telegram, расшифровать и восстановить их в пустые тестовые базы.

```bash
sudo cp deploy/systemd/maestro-database-backup.* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start maestro-database-backup.service
sudo systemctl enable --now maestro-database-backup.timer
sudo systemctl status maestro-database-backup.timer
```

## 5. Выкладка

Использовать единый deploy CRM + Learning Platform с точными SHA:

```bash
cd /var/www/maestro_crm
CRM_RELEASE_SHA_OVERRIDE=<crm-commit-sha> \
LP_RELEASE_SHA_OVERRIDE=<learning-commit-sha> \
./deploy/deploy-maestro-all.sh all
```

Скрипт должен до переключения версии:

- проверить SHA, environment и зависимости;
- сохранить backup обеих БД и проверить архивы;
- применить только versioned migrations;
- собрать приложения;
- сохранить предыдущие SHA и пути к backup в `deploy-state`;
- запустить health checks.

## 6. Проверка после выкладки

1. Открыть health endpoints CRM и Learning Platform; проверить БД и версию приложения.
2. Войти под администратором, преподавателем, учеником и родителем.
3. Создать в CRM тестовый урок, изменить формат online/offline, перенести, провести и подтвердить его в приложении.
4. Проверить обратное закрытие урока в CRM, посещаемость, начисление баллов/XP и отсутствие повторного начисления.
5. Назначить ДЗ, отправить его учеником с файлом, проверить преподавателем и убедиться в уведомлениях обеих сторон.
6. Проверить сообщения, файл до 50 МБ, родительскую видимость, новости, баланс и месячный план.
7. Проверить мобильные экраны Safari: навигацию, клавиатуру сообщений, длинные списки и отсутствие горизонтального скролла.
8. Проверить журналы без токенов, паролей, содержимого приватных файлов и персональных данных сверх необходимого.

## 7. Откат

- Не удалять pre-deploy backup и `deploy-state` до завершения наблюдения.
- Для кода вернуть оба приложения на `PREVIOUS_RELEASE_SHA`, сохраненные deploy-скриптом.
- БД восстанавливать только при несовместимой миграции или повреждении данных, из соответствующего проверенного pre-deploy backup.
- После отката повторить health checks и минимальный цикл CRM -> приложение -> CRM.

## 8. Граница готовности

Локальный release-кандидат готов. Финальный безусловный `GO` можно дать только после проверки production-конфигурации, ручного backup/restore с реальным Telegram и успешного smoke-теста сразу после выкладки. До этого документа production-сервер и production-БД не изменялись.
