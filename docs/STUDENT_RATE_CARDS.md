# Расценки ученика: действующая модель с 23 сентября 2026

Деньги хранятся только в `Student.accountBalance`. Подключённый тариф (`Membership.billingModel = rate_card`) задаёт стоимость видов занятий. Он не пополняет баланс, не покупает количество уроков и не ограничен сроком.

## Источник цены

Индивидуальный урок использует строку `individual`; теория — `theory`. Для групп обязательное назначение `Group.billingType`: `quartet`, `duo`, `trio` или `theory`. Число участников и название группы при текущем списании не определяют цену.

Сервер выбирает соответствующую строку `Membership.lessonRates` каждого ученика. Строка хранит исходную цену, скидку в процентах или тенге за один урок, причину и окончательную цену. Скидка применяется один раз, только к выбранной строке. Ноль с указанной причиной — бесплатное занятие; отсутствие строки — невозможность списания.

Нет подстановки 1200, цены другого формата, средней цены гибрида или цены направления. Если подходящих тарифов несколько, требуется явный выбор. Если цена изменилась после предварительного расчёта, подтверждение отклоняется и расчёт надо обновить.

## Работа администратора

1. Карточка ученика → подключить тариф / изменить расценки.
2. Выбрать шаблон либо указать персональные цены. Оставить включёнными только доступные виды занятий.
3. Указать скидку и причину по нужным строкам. При необходимости сохранить отдельный шаблон.
4. Проверить заменяемые назначения и сохранить. Старые записи архивируются, баланс и финансовая история не изменяются.
5. При создании/редактировании группы выбрать её назначение.

Шаблоны основной программы: 27 000 — индивидуальный 4000, квартет 2250, теория 1000; 50 000 — индивидуальный 3500, квартет 2250, теория 1000. Название программы не означает лимит, срок действия или автоматическое пополнение. Остальные персональные расценки хранятся отдельно.

Обычное подтверждение и платная отмена используют один механизм расценок. Подтверждение защищено транзакцией и блокировками от двойного списания. Отмена подтверждения возвращает фактически списанную сумму, даже если тариф затем заменён. Исторические счетчики старых покупок сохраняются для корректных возвратов, но не используются новым тарифом.

## Перенос старых данных

Сначала резервная копия PostgreSQL и версия кода, затем миграция схемы. `node scripts/audit-rate-cards.js` сохраняет снимок; `node scripts/migrate-rate-cards.js` выдаёт план без записи в БД. После проверки: `node scripts/migrate-rate-cards.js --apply /absolute/path/plan.json`.

План сохраняет однозначные персональные цены, включая бесплатные занятия, и оставшиеся экстренные отмены. Группы классифицируются по прежним явным настройкам; неоднозначные остаются без назначения. Неизвестные цены не выдумываются — они перечислены в `issues`. Перенос блокируется, если исходные назначения изменились после подготовки плана. Повторное применение того же плана запрещено.

Старые активные/замороженные назначения архивируются; старый каталог скрывается. Оплаты, история уроков, суммы прежних списаний, долги и денежные остатки не переписываются. Неактивным ученикам новые тарифы автоматически не назначаются.

## Совместимость и проверки

Обязательные старые колонки количества и дат оставлены в схеме для исторических записей. У новых тарифов они не управляют списанием; интеграционный API возвращает для срока и количества `null` вместе с `lessonRates`. Новые программы с лимитами нельзя создать старым API; пробная диагностика остаётся отдельным процессом.

Модульные проверки: `npm test`. Проверки реального PostgreSQL/HTTP: `TEST_DATABASE_URL=postgresql://.../maestro_ratecards_qa node --test test/rate-cards.db.test.js`. Последняя команда допускает только локальную тестовую БД. Старые DB-сценарии покупки программ относятся к прежнему контракту и не являются проверками нового тарифа.
