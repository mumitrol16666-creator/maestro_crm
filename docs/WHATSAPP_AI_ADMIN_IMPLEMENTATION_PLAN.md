# AI-администратор Maestro в WhatsApp

- **Статус:** план реализации
- **Дата:** 2026-08-09
- **Основной транспорт:** WhatsApp Web через Playwright
- **Резервный транспорт:** Selenium
**Системная таймзона:** `Asia/Aqtobe`

## 1. Цель

Создать управляемого AI-администратора, который работает с бизнес-номером школы в
WhatsApp и берёт на себя первичную обработку заявок:

- отвечает на вопросы о школе, направлениях, ценах и преподавателях;
- задаёт уточняющие вопросы и собирает карточку клиента;
- предлагает только реальные свободные слоты;
- записывает клиента на диагностический/пробный урок через CRM;
- выполняет запланированные повторные контакты;
- сообщает владельцу в Telegram, если не понимает запрос или не имеет права принять решение;
- позволяет владельцу мгновенно забрать и затем вернуть диалог;
- запускает только подтверждённые человеком рассылки по разрешённым сегментам;
- сохраняет историю сообщений, решений и действий для контроля качества.

Цель первого релиза — заменить администратора в типовом пути
`новое обращение → квалификация → предложение времени → запись на пробный`, а не
автоматизировать сразу все финансовые, конфликтные и нестандартные ситуации.

## 2. Принятые архитектурные решения

1. **Playwright — основной коннектор.** Он управляет выделенным Chrome с постоянным
   профилем WhatsApp Web.
2. **Selenium — холодный резерв.** Он реализует тот же интерфейс коннектора, но не
   запускается одновременно с Playwright на одном WhatsApp-аккаунте.
3. **Browser worker не пишет в PostgreSQL напрямую.** Он работает через закрытые
   внутренние API CRM. Бизнес-правила и аудит остаются в backend CRM.
4. **CRM — источник истины.** Цены, преподаватели, направления, заявки и расписание
   всегда читаются из CRM. Модель не имеет права запоминать и придумывать эти значения.
5. **Очереди MVP хранятся в PostgreSQL.** Отдельный Redis не требуется до появления
   реальной нагрузки.
6. **AI не дообучается на сырых диалогах в первой версии.** Сначала применяются
   версия промпта, база знаний, сценарии и tool calling. Размеченные диалоги позднее
   могут стать датасетом для отдельной оценки или дообучения.
7. **Все необратимые и рискованные действия имеют правила подтверждения.** Есть
   глобальный kill switch и блокировка автоматизации на уровне отдельного диалога.

## 3. Что уже есть и должно быть переиспользовано

- очередь ручных WhatsApp-напоминаний:
  `frontend/js/modules/whatsapp/reminders.js`;
- заявки, воронка и создание/перенос пробного: `backend/src/routes/bookings.js`;
- уроки, кабинеты и проверки конфликтов: `backend/src/routes/classes.js`;
- Telegram-клиент и конфигурация: `backend/src/utils/telegram.js`;
- единая политика диагностического урока: `backend/src/services/trialPolicy.js`;
- аналитика пробных: `backend/src/services/trialAnalytics.js`;
- уведомление клиентов об обработке WhatsApp-данных:
  `frontend/public/privacy.html`.

Нельзя дублировать проверку расписания внутри AI или browser worker. Агент только
вызывает CRM-инструменты, которые используют существующие серверные ограничения.

## 4. Целевая архитектура

```text
WhatsApp Web
    │
    ▼
Playwright worker ── heartbeat / QR / screenshots
    │ internal API
    ▼
CRM inbox + PostgreSQL queue
    │
    ▼
AI orchestrator ──────── база знаний и сценарии
    │                         │
    ├── CRM tools ────────────┤
    │   заявки / цены / слоты / запись
    │
    ├── Telegram escalation ── владелец / ручной перехват
    │
    ▼
Outbox ── approval / retry / idempotency
    │
    ▼
Playwright worker → WhatsApp Web
```

### 4.1. Процессы

#### `whatsapp-browser-worker`

- поднимает выделенный Chrome в headed-режиме;
- использует отдельный persistent profile;
- проверяет статус сессии и показывает QR только уполномоченному владельцу;
- читает новые и непрочитанные сообщения;
- загружает доступные медиа и передаёт метаданные CRM;
- расшифровывает голосовые через отдельную очередь;
- отправляет только сообщения, уже находящиеся в CRM outbox;
- подтверждает факт отправки и прикладывает технические доказательства;
- создаёт heartbeat и Telegram-аварию при logout/зависании;
- не принимает бизнес-решений.

#### `whatsapp-agent-worker`

- забирает необработанные входящие сообщения;
- обновляет структурированное состояние лида;
- выбирает сценарий и разрешённые инструменты;
- формирует ответ либо эскалацию;
- пишет решение и его основания в аудит;
- никогда не вызывает браузер напрямую.

#### CRM backend

- владеет контактами, заявками, расписанием, ценами и аудитом;
- валидирует каждое действие AI так же, как действие администратора;
- блокирует дубли, пересечения и запрещённые операции;
- управляет outbox, кампаниями и Telegram callbacks.

## 5. Browser connector

### 5.1. Сессия

- один WhatsApp-номер — один профиль Chrome;
- профиль хранится вне репозитория и резервных копий исходного кода;
- каталог профиля имеет права только у системного пользователя worker;
- одновременно разрешён один активный worker, контролируемый DB/advisory lock;
- при повторном запросе QR автоматическая отправка немедленно останавливается;
- после восстановления сессии worker сначала сверяет очередь, а не повторяет
  последние действия.

### 5.2. Получение сообщений

Для MVP используется сочетание DOM-наблюдателя и периодической сверки списка
непрочитанных диалогов. Для каждого сообщения сохраняются:

- стабильный внешний идентификатор, если он доступен;
- резервный fingerprint из чата, направления, времени и содержимого;
- направление `incoming`/`outgoing`;
- телефон или доступный идентификатор контакта;
- имя профиля;
- время WhatsApp и время получения CRM;
- тип: текст, аудио, изображение, документ, системное сообщение;
- текст или расшифровка;
- ссылка на локально сохранённое медиа;
- связь с заявкой/учеником;
- признак сообщения, отправленного человеком вручную.

Повторный импорт одного сообщения не должен создавать новую запись или повторный
ответ.

### 5.3. Отправка

- worker забирает только `queued`-сообщения;
- перед отправкой проверяет, что диалог не находится в `human_takeover`;
- после ввода повторно сверяет активный чат и получателя;
- сохраняет результат `sent`, `failed` или `uncertain`;
- статус `uncertain` не повторяется автоматически до сверки истории;
- несколько частей одного ответа отправляются в заданном порядке;
- при ручном исходящем сообщении автоматизация этого диалога ставится на паузу.

### 5.4. Selenium

Selenium реализует интерфейс `WhatsAppConnector`, идентичный Playwright:

```text
health()
listUnreadChats()
readConversation(chatId)
sendText(chatId, text, idempotencyKey)
downloadMedia(messageId)
openChat(chatId)
shutdown()
```

Переключение допустимо только после остановки основного worker и освобождения lock.

## 6. Предлагаемая модель данных

Названия финализируются при проектировании Prisma-схемы.

### `WhatsappBrowserSession`

Состояние авторизации, heartbeat, версия коннектора, время последнего входящего и
исходящего сообщения, причина остановки.

### `WhatsappContact`

Нормализованный телефон, имя профиля, связь с `Booking`/`Student`, согласие на
рассылки, дата последнего обращения, признак блокировки.

### `WhatsappConversation`

Контакт, ответственный режим, этап воронки, статус takeover, краткое резюме,
дата следующего контакта.

### `WhatsappMessage`

Внешний ID/fingerprint, направление, тип, содержимое, media metadata, автор
`client|agent|human|system`, статус доставки.

### `WhatsappAgentThread`

Структурированные факты, текущая цель, ожидаемый ответ пользователя, уверенность,
версия промпта и базы знаний.

### `WhatsappOutbox`

Получатель, текст, порядок, idempotency key, источник, необходимость подтверждения,
статус, число попыток и последняя ошибка.

### `WhatsappEscalation`

Причина, выдержка диалога, предложенный ответ, Telegram message ID, решение человека,
время ответа и итог.

### `WhatsappCampaign` / `WhatsappCampaignTarget`

Сегмент, контент, dry-run, согласование, расписание, лимиты и результат по каждому
адресату.

### `AiKnowledgeArticle`

Тип знания, содержимое, структурированные значения, версия, статус
`draft|published|archived`, автор и дата публикации.

### `AiAgentAction`

Полный аудит tool calls: входные данные, разрешение, результат, ошибка, инициатор и
correlation ID. Секреты и полное содержимое системного промпта не логируются.

## 7. Состояния диалога

```text
new
  → qualifying
  → awaiting_client
  → qualified
  → slots_offered
  → slot_held
  → trial_booked
  → follow_up
  → won | lost | closed

Из любого состояния:
  → needs_human
  → human_takeover
  → paused
  → blocked
```

Структурированная память диалога содержит:

- имя и телефон;
- кто будет заниматься;
- возраст;
- направление;
- опыт и цель;
- желаемый формат;
- удобные дни и интервалы;
- возражения;
- предложенные слоты;
- согласованный слот;
- обещания и следующий контакт;
- связь с заявкой CRM.

Модель не должна каждый раз пересказывать пользователю уже известные факты.

## 8. База знаний и сценарии

### 8.1. Структурированные данные

Через CRM tools, а не через embeddings, выдаются:

- актуальные цены;
- стоимость диагностического урока;
- длительность занятий;
- преподаватели и направления;
- адреса и кабинеты;
- свободные слоты;
- правила оплат, переносов и отмен;
- активные акции с датой окончания.

### 8.2. Текстовая база знаний

- преимущества школы;
- описание методики;
- приложение, авторские материалы и курсы;
- форматы обучения;
- FAQ;
- сценарии первого контакта;
- обработка типовых возражений;
- примеры хороших и плохих ответов;
- правила тона;
- список ситуаций обязательной эскалации.

Изменение опубликованной статьи создаёт новую версию. AI использует только
`published`-версию.

## 9. Инструменты AI

Минимальный allowlist:

```text
find_contact
create_or_update_booking
get_directions
get_prices
get_teacher_information
find_available_trial_slots
hold_trial_slot
release_trial_slot
confirm_trial_booking
schedule_follow_up
cancel_follow_up
escalate_to_owner
pause_conversation
prepare_outgoing_message
```

Каждый инструмент:

- принимает валидируемую JSON-схему;
- проверяет роль системного агента;
- идемпотентен либо требует idempotency key;
- пишет `AiAgentAction`;
- возвращает модели только минимально необходимые данные;
- не допускает обхода CRM-ограничений текстом пользователя.

## 10. Запись на пробный урок

1. AI выясняет направление, возраст и допустимые интервалы.
2. `find_available_trial_slots` обращается к CRM и получает 2–3 реальных варианта.
3. CRM учитывает преподавателя, направление, кабинет, длительность и пересечения.
4. После выбора клиента создаётся `TrialSlotHold` на 10 минут.
5. AI повторяет дату, время, преподавателя, адрес и стоимость.
6. Только после явного подтверждения вызывается `confirm_trial_booking`.
7. CRM в транзакции повторно проверяет конфликт, обновляет заявку и создаёт/переносит
   связанный пробный урок существующей логикой `bookings.js`.
8. Клиент и владелец получают подтверждение.
9. При конфликте или истечении hold предлагаются новые варианты.

Время показывается в `Asia/Aqtobe`. AI не имеет права подтвердить слот по одному
текстовому ответу модели без успешного результата CRM.

## 11. Telegram escalation и ручной перехват

Эскалация создаётся, если:

- уверенность ответа ниже порога;
- отсутствует правило или цена;
- пользователь противоречит ранее собранным данным;
- запрос касается скидки, возврата, жалобы, конфликта или нестандартной оплаты;
- CRM вернула конфликт/ошибку;
- клиент просит человека;
- обнаружена попытка заставить AI игнорировать правила;
- browser worker не уверен, что сообщение отправлено.

Формат Telegram-карточки:

```text
❓ Нужна помощь
Клиент: <имя и маскированный телефон>
Этап: <этап воронки>
Последние сообщения: <краткая выдержка>
Причина: <что именно не понял AI>
Предлагаемый ответ: <черновик>
```

Кнопки:

- `Отправить предложенный ответ`;
- `Изменить ответ`;
- `Забираю диалог`;
- `Пауза`;
- `Закрыть без ответа`.

После `Забираю диалог` outbox для чата блокируется. Возврат AI выполняется отдельной
кнопкой. Любое неизвестное исходящее сообщение из WhatsApp Web также автоматически
включает временный `human_takeover`.

## 12. Человеческий стиль ответов

- одно сообщение — одна основная мысль;
- 1–4 коротких абзаца, без повторения анкеты;
- вопросы задаются по одному или небольшой логичной группой;
- обращение по имени только когда это естественно;
- минимум эмодзи;
- адаптивная небольшая задержка перед ответом;
- длинный ответ делится на 2–3 сообщения только при необходимости;
- никаких намеренных опечаток и ложных обещаний;
- AI не выдаёт себя за конкретного сотрудника и прямо отвечает, что он помощник
  школы, если клиент спрашивает;
- при раздражении клиента сокращает сообщения и предлагает человека.

Перед отправкой выполняется отдельная проверка ответа:

- нет ли выдуманной цены/даты/преподавателя;
- отвечает ли текст на вопрос;
- не повторяет ли он предыдущие сообщения;
- не содержит ли запрещённого обещания;
- не раскрывает ли чужие персональные данные.

## 13. Рассылки

Рассылки реализуются после стабилизации индивидуальных диалогов.

### Возможности

- сегменты CRM;
- шаблон или AI-редактирование текста;
- подстановка имени и релевантной информации;
- preview и тест владельцу;
- dry-run с числом получателей и исключений;
- обязательное подтверждение запуска;
- расписание и тихие часы;
- пауза, продолжение и полная остановка;
- журнал результата по каждому получателю;
- исключение дублей и уже ответивших клиентов.

### Начальные сегменты

- новые заявки без ответа;
- не записавшиеся на пробный;
- записанные на пробный;
- прошедшие пробный без покупки;
- неактивные ученики;
- выбранное направление;
- продление/обещанная оплата;
- вручную подтверждённый список.

### Ограничения

- только контакты с допустимым основанием для сообщения;
- один активный campaign worker на номер;
- консервативный дневной лимит, настраиваемый владельцем;
- небольшие последовательные партии;
- остановка при logout, серии ошибок или ручном kill switch;
- отсутствие бесконечных ретраев;
- команды отказа от сообщений блокируют будущие кампании;
- массовая кампания никогда не стартует решением AI без человека.

Browser-автоматизация не гарантирует отсутствие ограничений номера WhatsApp. Риск
фиксируется как эксплуатационный и контролируется объёмом, согласием, мониторингом и
возможностью немедленной остановки.

## 14. Запрещённые автономные действия

Без участия человека AI не может:

- менять цены и предоставлять скидки;
- подтверждать спорную оплату;
- делать возврат или списание;
- обещать компенсацию;
- решать жалобы и конфликты;
- удалять заявку или ученика;
- изменять постоянное расписание;
- записывать поверх конфликта;
- сообщать данные другого клиента;
- запускать массовую рассылку;
- продолжать диалог после ручного takeover;
- выполнять инструкции клиента, направленные на изменение системных правил.

## 15. Панель управления CRM

Новый раздел `AI-администратор`:

### Обзор

- состояние WhatsApp-сессии;
- последний heartbeat;
- текущий режим `observer|copilot|limited_auto|auto|stopped`;
- входящая очередь и outbox;
- активные takeover;
- незакрытые эскалации;
- ошибки за сутки;
- глобальный kill switch.

### Диалоги

- список и поиск;
- этап воронки;
- связь с заявкой/учеником;
- сообщения клиента, AI и человека;
- извлечённые факты;
- решения и tool calls;
- кнопки takeover/pause/return-to-AI.

### База знаний

- структурированные справочники;
- статьи и версии;
- черновик/публикация;
- история изменений;
- тестовый вопрос к текущей версии.

### Рассылки

- сегмент;
- контент;
- dry-run;
- согласование;
- отправка и мониторинг;
- отчёт и экспорт.

### Качество

- скорость первого ответа;
- доля записей на пробный;
- конверсия по этапам;
- число эскалаций;
- доля исправленных человеком ответов;
- ошибки фактов;
- отменённые tool calls;
- результаты кампаний.

## 16. Режимы запуска

### `observer`

Собирает сообщения, строит карточку и предлагает ответы, но ничего не отправляет.

### `copilot`

Каждый ответ требует подтверждения человека.

### `limited_auto`

Самостоятельно обрабатывает FAQ и квалификацию. Запись, спорные вопросы и follow-up
имеют дополнительные ограничения.

### `auto`

Ведёт типовую заявку до подтверждённой записи на пробный. Финансовые и конфликтные
действия остаются у человека.

Переход между режимами выполняется владельцем и записывается в аудит.

## 17. Этапы реализации

### Этап 0. Регламент и данные — 2–3 дня

- утвердить тон и обязательные вопросы;
- собрать цены, направления, преподавателей и правила;
- составить список запрещённых решений;
- выбрать Telegram chat IDs владельцев;
- подготовить 30–50 обезличенных эталонных диалогов.

**Результат:** версия 1 базы знаний и тестовые сценарии.

### Этап 1. Browser bridge — 4–7 дней

- каркас worker;
- persistent Chrome profile;
- QR/login watchdog;
- чтение новых сообщений;
- импорт истории доступного чата;
- outbox и безопасная отправка;
- дедупликация, heartbeat, screenshots;
- Telegram-аварии.

**Результат:** CRM получает и отправляет сообщения без AI.

### Этап 2. Inbox и режим наблюдателя — 4–6 дней

- Prisma-модели;
- internal API;
- экран диалогов;
- связь контакта с заявкой;
- структурированная память;
- аудит действий;
- глобальная остановка.

**Результат:** полная наблюдаемая история WhatsApp в CRM.

### Этап 3. AI copilot — 5–8 дней

- база знаний и версии;
- сценарий квалификации;
- генерация коротких ответов;
- проверка фактов;
- confidence routing;
- Telegram escalation/takeover;
- защита tool calling и prompt injection.

**Результат:** AI предлагает ответы, человек подтверждает.

### Этап 4. Расписание и пробные — 4–7 дней

- API свободных слотов;
- `TrialSlotHold`;
- предложение вариантов;
- подтверждение клиентом;
- транзакционная запись через существующую booking-логику;
- перенос/истечение hold;
- уведомления.

**Результат:** AI безопасно записывает на пробный.

### Этап 5. Ограниченный автопилот — 7–14 дней

- автоматический FAQ и квалификация;
- follow-up;
- контроль ручных исходящих;
- ежедневный QA-отчёт;
- исправление сценариев по реальным диалогам.

**Результат:** типовые заявки обрабатываются без администратора.

### Этап 6. Рассылки — 4–6 дней

- сегментация;
- campaign builder;
- preview/dry-run/approval;
- очередь, лимиты и quiet hours;
- отписки;
- отчёт по каждому получателю.

**Результат:** контролируемые WhatsApp-кампании из CRM.

### Этап 7. Стабилизация — 7–14 дней

- Selenium fallback;
- восстановление после обновлений WhatsApp Web;
- нагрузочные и аварийные тесты;
- эксплуатационная документация;
- обучение владельца;
- финальная приёмка.

Ориентир: первый copilot через 2–3 недели, запись на пробный и ограниченный автопилот
через 4–6 недель, рассылки и стабилизация через 6–8 недель.

## 18. Тестовые сценарии

1. Новый клиент спрашивает только цену.
2. Клиент отвечает на вопросы в разном порядке.
3. Клиент отправляет голосовое сообщение.
4. Клиент просит время, которого нет.
5. Два клиента одновременно выбирают один слот.
6. Hold истекает до подтверждения.
7. CRM возвращает конфликт при финальной записи.
8. Клиент меняет направление в середине разговора.
9. Клиент просит скидку или возврат.
10. AI не знает ответа и создаёт Telegram escalation.
11. Владелец забирает диалог и пишет вручную.
12. Ручное сообщение обнаруживается без Telegram-кнопки.
13. Worker падает после ввода, но до подтверждения отправки.
14. Worker перезапускается с очередью сообщений.
15. WhatsApp запрашивает QR повторно.
16. Пользователь пытается заставить AI игнорировать инструкции.
17. Кампания проходит dry-run и тестовую отправку.
18. Кампания останавливается при серии ошибок.
19. Контакт отказывается от рассылок.
20. Один человек существует одновременно как заявка и ученик.

## 19. Критерии приёмки MVP

- после перезапуска не появляются дубли входящих или исходящих сообщений;
- logout WhatsApp блокирует outbox и создаёт Telegram-аварию;
- ручной ответ гарантированно включает takeover;
- AI не называет цену без успешного CRM tool result;
- AI не подтверждает слот без CRM confirmation;
- двойная запись на один ресурс блокируется;
- владелец может остановить AI глобально и для отдельного чата;
- Telegram escalation содержит контекст и позволяет ответить/забрать чат;
- каждое сообщение и tool call имеет audit record;
- режим `observer` не способен отправлять сообщения;
- рассылка не стартует без dry-run и подтверждения;
- ошибки browser worker видны в `/health` и CRM;
- персональные данные не попадают в технические логи и системные ошибки.

## 20. Мониторинг и эксплуатация

Контролировать:

- browser session online/offline;
- возраст heartbeat;
- время последнего входящего/исходящего;
- размер inbox и outbox;
- `uncertain`-отправки;
- число ретраев;
- Telegram escalation SLA;
- число takeover;
- ошибки AI tools;
- ошибки расписания;
- campaign error rate.

Аварийные уведомления отправляются при logout, зависшем heartbeat, серии ошибок
отправки, росте очереди, недоступности CRM/LLM и конфликте worker lock.

## 21. Безопасность и данные

- browser profile и cookies не попадают в Git;
- internal API использует отдельный service token и IP/network restriction;
- worker получает только минимальные права;
- медиа хранится ограниченное время;
- телефоны маскируются в логах и Telegram-превью;
- доступ к диалогам ограничивается ролями;
- экспорт и массовая рассылка записываются в аудит;
- предусмотрены сроки хранения и удаление по запросу;
- резервные копии шифруются;
- системный промпт не содержит токенов и паролей;
- текст клиента считается недоверенным вводом и не может расширять tool permissions.

## 22. Риски

| Риск | Мера |
|---|---|
| WhatsApp Web изменил DOM | семантические локаторы, smoke tests, screenshots, быстрый adapter update |
| Слетела сессия | heartbeat, блокировка outbox, Telegram QR alert |
| Повторная отправка | idempotency key, fingerprint, статус `uncertain`, сверка истории |
| Ограничение номера | консервативные рассылки, согласование, лимиты, kill switch |
| Галлюцинация цены/слота | только CRM tools, финальный factual validator |
| Двойное бронирование | slot hold и повторная транзакционная проверка |
| AI продолжил после человека | takeover detection и блокировка outbox |
| Prompt injection клиента | tool allowlist, раздельные инструкции/данные, policy validator |
| Недоступна модель | очередь сохраняется, клиенту не отправляется выдуманный fallback |
| Утечка переписки | role access, masking, retention, encrypted backups |

## 23. Порядок начала работ

Первый технический спринт должен включать только:

1. Prisma-модели session/contact/conversation/message/outbox;
2. internal API;
3. Playwright persistent profile и login watchdog;
4. импорт новых текстовых сообщений;
5. ручную отправку через CRM outbox;
6. дедупликацию и статус `uncertain`;
7. Telegram-аварию при logout;
8. режим `observer` без AI-автоответов.

AI, запись на пробный и рассылки нельзя начинать до прохождения приёмки browser
bridge. Это уменьшает вероятность потерять диалог, отправить дубль или записать
клиента на неверное время.
